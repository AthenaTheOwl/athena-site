## FINDING ONE: AN APPROVAL HAS AN OBJECT.

A reviewer accepts a proposal. Someone changes the proposal. The status remains approved because the system stores the decision against a filename, ticket or feature name.

Nothing dishonest has to happen. A source gets corrected. A test fixture changes. A paragraph is rewritten after review to sound more certain. The workflow remembers that the reviewer said yes and forgets what the reviewer saw.

[AI Product Team](https://github.com/3orionkings/ai-product-team), an October 2026 package of specialist roles and workflows, puts this problem near the center of its design. Its case ledger binds records to content hashes and treats approval as covering a particular version. The [reviewed source snapshot](https://github.com/3orionkings/ai-product-team/tree/13d66592ad5d9486dea8910987918d11f0456bca) also states the limit: the workflow rules are instructions in this release; the experimental controller is not connected to the hosts.

That is a useful proposal with an explicit boundary. A model can be told to notice changed evidence. A publishing function can be made unable to ignore it.

## FINDING TWO: A HASH CAN ANSWER ONLY THE QUESTION IT WAS GIVEN.

A digest answers whether the bytes match. It does not answer whether the report is good, whether the source is correct, or whether the reviewer had authority to approve it.

It also cannot protect an input nobody included.

Suppose the reviewed report contains a revenue estimate derived from a CSV. The report's bytes stay the same while the CSV is corrected. A digest of the report alone still matches. If approval depends on the calculation, the review needs the relevant input version as well.

The hard work is specifying the dependency. An approval record should name the artifact, the evidence it relies on, the check performed and the scope of the decision. Hashing everything in sight is expensive and can still miss the live service that supplied a number. Hashing one convenient output is cheap and can preserve the wrong conclusion perfectly.

REVIEW SCOPE

Question answered: does this draft satisfy these checks against these inputs?
Question left open: will a later draft satisfy them against later inputs?

## FINDING THREE: HISTORY SHOULD SURVIVE INVALIDATION.

The old test result remains a fact: that command returned that status against that version. The mistake is making it a fact about the current version.

A useful ledger keeps both statements. The earlier check passed. A later change made the check insufficient for the proposed release. The record is not erased; its applicability ends.

This matters when a system tries to “refresh” evidence by replacing yesterday's file. A clean dashboard can conceal that nobody ran the test again. An append-only history with explicit versions makes the gap visible.

The distinction also makes corrections less punitive. A source can be superseded without pretending it never existed. A reviewer can have made a sound decision on the information available and still need to review again. The system has to represent both facts without asking a person to withdraw an honest historical statement.

## FINDING FOUR: THE CHECK AND THE ACTION MUST SEE THE SAME OBJECT.

There is another failure window after a digest is recorded. A publisher checks the file, then opens it again to copy it. The file changes between those operations. The check was correct. The published object is different.

For a small file, the simplest boundary is to read once, check those bytes and publish those bytes. For a database or remote object, the corresponding control is a conditional operation against the version read.

HTTP already has a vocabulary for that. [RFC 9110, section 13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1), defines `If-Match` using strong entity-tag comparison and describes its use in preventing lost updates. The server checks the condition before applying the method. A client remembering an earlier check is weaker than a server enforcing the precondition at the mutation.

The general requirement is the same: the version check belongs beside the action whose authority depends on it.

## FINDING FIVE: A REVIEW ROLE IS NOT AN ENFORCEMENT BOUNDARY.

A specialist can find contradictions. An adversarial reviewer can propose a test that would settle one. A dispatcher can keep those jobs separate and avoid paying for roles the task does not need. These are useful ways to organize attention.

They become controls only where an action depends on their result.

If a writer can mark its own artifact approved and the publisher accepts that field, the role names supply no separation. If the publisher rejects an artifact whose digest differs from the reviewed digest, that particular boundary exists even when the model forgets the instruction.

This suggests a selective adoption rule. Take a workflow's strongest invariant and ask where it can fail closed in the existing application. A small digest check at publication can do more for a stale-review bug than a large directory of reviewers. The reviewers can then spend their effort on the question the digest cannot answer: whether the content deserves approval.

## THE EXPLANATIONS AFTERWARD

*The first explanation was that the cure would cost more than the edit.*

**Objection:** Requiring a new review after every change makes small edits expensive.

**Reply:** The approval can have a narrower scope. A spelling correction need not rerun a model comparison if the system can establish that the compared inputs and outputs are unchanged. But that is an explicit dependency rule. “Probably harmless” is a judgment that needs an owner.

*The second explanation was that an instruction could be sufficient.*

**Objection:** The model can follow a version rule without a controller.

**Reply:** It can, and a successful run is evidence that it did. It is weaker evidence that a later run must. The decisive test changes an approved artifact and attempts the action again. Rejection at that boundary establishes a property that a well-written review instruction alone cannot establish.

That test could also overturn the criticism of any particular workflow. If a host enforces the version dependency at publication, the promised control exists there. Its location matters less than the fact that the changed object cannot borrow the earlier yes.
