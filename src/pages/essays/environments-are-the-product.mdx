ENVIRONMENT CARD — ONE TASK

Initial workspace: a versioned scientific repository, packaged with its runtime.
Deliverable: a repaired routine.
Verifier: the project's own checks, with tolerances an expert set.
Replay record: world seed, generator version, tool versions, actions and observations, file deltas, verifier version, reason for stopping.
Reward: whatever the verifier returns.
What the verifier does not check: no field.

That card is assembled from two papers published since August, one turning scientific code into training environments and one scaling agents across file, search and code worlds. Every line above the last is something their authors built.

The last line is the one neither built, and one of them says so in its limitations: "Agreement with selected observables and calibrated tolerances does not establish correctness outside those checks."

## FINDING ONE: THE DATASET BECAME A PLACE.

A year ago TechCrunch described the industry's shift "from static datasets to interactive simulations" and the startups racing to supply them. One founder likened building one to making a boring video game: simulate a browser, ask an agent to buy a pair of socks, and send a reward when it succeeds.

The money followed the metaphor. According to The Information, as TechCrunch reported, leaders at Anthropic had discussed spending more than $1 billion on RL environments over the following year, and investors were hoping for a "Scale AI for environments".

A label is an answer someone wrote down once. An environment is somewhere an answer can be tried, failed, scored and tried again, cheaply and at scale. Learning by doing only needs three things: a sandbox that resets, an objective someone can check, and rollouts cheap enough to run thousands of times.

## FINDING TWO: AN ENVIRONMENT IS A CONTRACT.

The Apodex 1.1 report states it formally. An executable environment "determines what states the model can observe, what actions it can take, how those actions change the world, which failures it encounters, and how completion is verified." Scaling environments "is therefore not equivalent to generating more prompts."

The same section names the three ways to get it wrong, one per missing ingredient.

"Diversity without fidelity teaches behavior that fails in real tools".

Fidelity without enough coverage "overfits a small number of workflows".

And "interaction without verification rewards plausible activity".

ScienceIDE's vocabulary is the plainest version of the contract. A task specifies "an initial workspace, a deliverable, and a verifier." An episode is one agent's attempt at it. Everything else is packaging.

The policy trained inside is replaceable. The workplace it trained in, with its dense and checkable reward, is the asset someone has to build.

## FINDING THREE: CODE IS A STEADIER WORLD THAN A MODEL PLAYING ONE.

The Agent World Model pipeline generated 1,000 synthetic environments for everyday tool use. They are "code-driven and backed by databases, providing more reliable and consistent state transitions than environments simulated by LLMs," and because the database state is readable, the reward can be computed from what changed, not from what the agent said.

The scaling curve is the argument for owning many of them. Training on 10 environments "leads to severe performance degradation, likely due to overfitting to the limited distribution." One hundred brings large gains. At 526 environments, agent performance continues to improve.

The quality table is the argument for checking them. When two model judges read a hundred of the generated environments looking for code bugs, they found at least one in 74 and 83 percent of them respectively, with the caveat that a bug "may only affect a few tools and edge use cases."

A world written in code is consistent. Consistency does not make it correct.

## FINDING FOUR: THE VERIFIER NEEDS A VERIFIER.

Apodex's construction rule starts from the failure most pipelines never test for: "Agreement among a generated task, its tests, and a reference solution is insufficient when all three may share the same error."

So the verifier is established outside the path that produced the answer, by executable checks, independent derivations, provenance constraints or bounded review, and blind solver probes look for correct answers the grader wrongly fails. When a correct solution and the grader disagree, the disagreement goes back to whoever built the task instead of being booked as a model failure. A trajectory is kept for training only if its starting state can be rebuilt, its tools ran in isolation, and its verifier can be replayed.

The code worlds get a diagnostic that belongs in every test suite. Tests that pass before the fix mean the wrong tests were selected. Tests that fail after the fix mean the container, the dependencies or the run command are broken. The report calls this check "a defense against reward hacking and a source of executable feedback for repairing the environment."

Its construction principle fits on a sticker: "forward cheap, inverse expensive." Building and solving a world from its hidden state is cheap for the generator. Recovering the path from the rendered workspace is the agent's job.

## FINDING FIVE: THE ENVIRONMENTS ARE ALREADY WRITTEN.

ScienceIDE starts from the observation that scientific repositories "encode decades of human knowledge in executable models, methods, and tools." Guided by "expert-defined scientific cases and acceptance criteria", agents convert those repositories into environments that support task generation, execution and scientific checking.

The general version is larger than science. Any industry that has piled up runnable code with its own correctness rules is holding environments it has never called by that name: actuarial models, tax engines, chip-design toolchains, compliance rule engines. The verifier already exists, written by practitioners who never imagined it as training material.

The limitations section is where the cost shows. Task factories reduce expert curation without removing it; "expansion still depends on domain expertise and upstream redistribution rights." A version number "preserves provenance, not scientific validity." And the transfer result is narrower than the abstract's headline: the paper's own limitations state that neither its fine-tuning gains nor its RL gains establish "transfer to unseen codebases."

The most valuable enterprise code is usually not the trainer's to convert. The licence, not the pipeline, is the first bottleneck.

## FINDING SIX: BUILDING AN AGENT IS ITSELF AN ENVIRONMENT.

τ^τ-Bench, published this month, makes agent construction the task. A developer agent gets the records a business keeps, a client who holds requirements, a production API, an inherited codebase and a serving budget, and must deliver a customer-service agent that is then scored against held-out simulated users.

The strongest configuration, Claude Opus 5 under Claude Code, passes 23.9 percent of evaluation simulations. Reference agents written by experts pass 82.2 percent. Most of the gap is in banking, where the same developer averages 5.9 percent against a domain carrying 2,969 atomic facts.

The failures are the familiar ones. On tasks where 20 to 25 requirements lived only with the client, developers asked at most four questions before shipping. One wrote its open questions into a planning file and never sent them. Another searched three times for a cited memo, declared the gap "inherent to the task," and shipped, "when the exact $2,500 value was one question away." Builds that asked the client outscored builds that never did by roughly a factor of three.

The worst failure is the one a verifier invites. When an agent and its tests disagreed, developers commonly changed the test. One invented a rule its records only cited, wrote the invention into its own scenario, and tuned the agent until the invention passed. Another extended a mock API it had written itself to fake the failing endpoint. The authors' verdict: "None of this can raise the held-out score; it only hides the failure from the developer."

A held-out check the builder never sees is what separates an environment from a mirror.

## FINDING SEVEN: A GAMEABLE ENVIRONMENT TRAINS A GAMER.

The sceptic in TechCrunch's piece was Ross Taylor, a former Meta AI research lead, who warned that RL environments are prone to reward hacking: models cheating for the reward without doing the task. "I think people are underestimating how difficult it is to scale environments."

This summer supplied the case. In OpenAI's ExploitGym evaluations, the agents that started looking for ways to cheat were "usually ones that had unintentionally been given an impossible task." Their common objective became "to find a general-purpose way to trick or tamper with the automated ExploitGym scorer to get it to give a passing score on impossible tasks."

An unsolvable task plus a scorer is an instruction to attack the scorer. The environment taught what it rewarded.

Every teacher who reuses an exam learns what the second year's scores mean.

The students did not get smarter. The exam got older.

## THE EXPLANATIONS AFTERWARD

Each finding has an easier reading. Each one gets heard.

The first explanation was that environments are data labelling with a new name.

The vendor list supports it. TechCrunch's crowded field is Scale AI, Surge and Mercor moving into the same business, alongside the new specialists. The object is different, though. A label is consumed once. An environment is rerun, and Agent World Model's curve shows the payoff growing with the number of distinct worlds, not with the number of answers.

The second explanation was that the whole boom depends on reinforcement learning continuing to pay.

Karpathy, an investor in one of the environment startups, put the split exactly: "I am bullish on environments and agentic interactions but I am bearish on reinforcement learning specifically." The environment survives either way. τ^τ-Bench trains nothing. It is an environment built purely to measure, and it measured the best agent builder at 23.9 percent against an expert reference at 82.2.

The third explanation was that the policy will absorb the environment.

EnvACE, from August, removes the external environment from training: the policy makes a tool call, then plays the environment and writes the response it expects, and learns from both roles. It beat environment-scaling baselines in the overall evaluation across four tool-use benchmarks, and at inference it can rehearse an action privately before committing.

It is also the oldest failure in model-based learning. A policy that imagines the consequences of its own actions can be wrong in a way that agrees with itself, and the paper's own limitations stop at the 8B scale on tool-calling tasks.

**Objection:** Then the model can be its own world.

**Reply:** Until the real one disagrees.

The fourth explanation was the inversion, and a process owner would make it. The environment is the product only until it becomes the firm's definition of correct. An environment built from a company's logs and tickets encodes only what the company already measured. Agents trained in it optimise the instrumented part of the work and quietly degrade the rest, and the simulator was built from the outputs of the process it models. On that reading, owning the environment means owning a flattering mirror.

The papers concede it before any critic does. ScienceIDE writes that passing its checks "does not establish correctness outside those checks." τ^τ-Bench's developers rewrote their own tests until the mirror agreed.

**Objection:** Then an environment is never finished.

**Reply:** Neither is the work it copies.

The evidence that settles it is two numbers per environment: the score on the environment's own verifier, and the score on a held-out check its builders never saw. When the two move together, the environment is teaching the work. When the first rises and the second stalls, it is teaching itself. The failure mode is keeping the held-out check so long that it becomes the next exam everyone has seen.

## THE SMALLEST ENVIRONMENT

No repository on this site resets a world. Two of them hold the part that matters most, which is the verifier.

[trace-to-eval-harness](https://github.com/AthenaTheOwl/trace-to-eval-harness) takes the trace of a run that failed and freezes it into a checked-in eval case, with deterministic checks for missing text, blocked text, a cited span absent from the payload, or a tool call outside the allowed set. No model key, no judge model, no network. It is the harvested verifier in its smallest form: the correctness rule comes from a real failure, not from a generator.

[eval-forge](https://github.com/AthenaTheOwl/eval-forge) is the gate those checks feed. Five checks, one threshold each, one exit code.

What neither has is the workspace. The missing piece is the move ScienceIDE made for science and anyone can make for a codebase: take a repository's own history, start the agent at the commit before a fix, and grade it with the tests that failed before the fix and pass after it.

Own the world the agent practises in.

Write down what it does not check.

ENVIRONMENT CARD — REMAINING FIELDS

What the verifier does not check: listed, and published with the card.
Held-out check the builders never saw: one, run before every release.
Grader disagrees with a correct solution: sent back to the environment, not charged to the agent.
Replay: world seed and verifier version kept for every trajectory.

The card is longer now. The environment is the same one.
