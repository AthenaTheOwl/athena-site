A spec answers what is being built and how completion will be checked. Product repos keep a numbered ledger under `specs/NNNN-<slug>/`. Amend it on the record when the answer changes.

A requirement written before implementation gives the review something independent to compare. It can still be the wrong requirement.

## What the ledger holds

The inspected product-repo `spec_check.py` scripts require six files: `requirements.md`, `design.md`, `tasks.md`, `acceptance.md`, `research.md` and `traceability.md`. The requirements use the repo's `R-PREFIX-NNN` identifiers. Traceability connects each requirement to the records meant to resolve it.

The scripts check file presence, recognized requirement ids and links to decisions, with explicit deferrals where supported. They do not execute every prose acceptance criterion or establish that an implementation meets its intent.

Structure is the cheap part worth automating.

## A concrete example

Ai-field-brief's `specs/0010-cognitive-delivery-control-plane/requirements.md` names dream-output validation as `R-CDCP-003`. It reserves a shared schema contract and describes the validator as future work to land with the first real output. That is a requirement, not evidence the validator had already shipped when the spec was written.

The same spec names decision conformance, release records, reset records and the agent contract. Each requirement has acceptance text a reviewer can inspect. The separate task and traceability files say how that work is organized.

## What a requirement needs

Name the behavior, the condition under which it matters and an observable acceptance check. Give the requirement a stable id so a decision and test can point back to it. A malformed-record test can establish rejection of that malformed record; it cannot establish that every invalid record is rejected.

When a test passes before the proposed implementation, ask whether the behavior already exists or the check misses the requirement. Do not count the green result twice.

## Why the ledger comes first

Changing a sentence is usually cheaper than changing a system built around it. The ledger makes that early disagreement visible. It also needs a revision path: discoveries during implementation can invalidate a plan without making the implementation wrong.

Compare a spec-led change with the defect and rework it avoids. More numbered files are an administrative output. Fewer unresolved requirements are the result the ledger is for.
