An artifact is something made during a run that should outlive the run: a patch, a review, an eval report, a screenshot. Its record identifies the output and the work that produced it. The shared contract is `ops/schemas/artifact.schema.json`.

A file can survive without that record. What becomes harder is finding out what the file was evidence for.

## What the record carries

The schema requires eight fields:

- `id` and `type`: the stable identifier and artifact category.
- `spec_id`: the spec the output serves.
- `produced_by` and `run_id`: the producer and the run.
- `status`: proposed, accepted, superseded or rejected.
- `summary`: what the output is.
- `evidence`: typed references supporting it.

A path belongs in an evidence reference. `artifact_path` and `requirement_id` are not fields in this schema. Requirement-level traceability has to be supplied through the surrounding spec and decision records.

## A concrete example

`supplier-risk-rag-agent/reports/baseline_eval_report.html` is a checked-in report. The following is an illustrative record in the shared format, not a claim that this exact metadata file accompanied that report:

```json
{
  "id": "example-baseline-report",
  "type": "eval_report",
  "spec_id": "specs/0004-evals/",
  "produced_by": "science.eval-runner",
  "run_id": "example-baseline-run",
  "status": "proposed",
  "summary": "Baseline report awaiting review.",
  "evidence": [
    {"kind": "report", "ref": "reports/baseline_eval_report.html"}
  ]
}
```

The example shows the joins the record permits. It supplies no new eval result. A schema check can reject missing fields; checking that the referenced report exists and supports the summary is another operation.

## Why typed records

A directory listing answers which files are present. Typed records let a consumer ask which outputs belong to a spec, which remain proposed and which run incurred their cost.

The type does not authenticate the producer. The reference does not pin the bytes unless it names a revision or digest. If the report changes after review, an unchanged path is still the same path. It is a different piece of evidence.

## The common types

The schema includes `patch`, `pr`, `eval_report` and `postmortem`, alongside reviews, traces and other outputs. Use the type that lets the next consumer interpret the record. Store the content where that repo's workflow expects it, and make the reference resolvable.

The durable unit is the output plus enough provenance to inspect it. A folder named `artifacts` is optional. The question it answers is not.
