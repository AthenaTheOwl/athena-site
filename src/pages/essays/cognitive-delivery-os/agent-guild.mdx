A guild is a cluster of roles that share a discipline. The portfolio names twelve: control, product, research, design, engineering, science, security, operations, domain, learning, documentation, commercial. Each repo declares its roles under `.agents/roles/<id>/role.yaml`.

The file describes the job. It does not, by existing, take a tool away from the runtime.

## The role file

The contract lives in `ops/schemas/role.schema.json`. Its required fields are `id`, `guild`, `mission`, `inputs`, `outputs`, `allowed_tools`, `forbidden_actions`, `required_gates`, `escalation` and `permissions`. The permissions object separates reading, writing, tests, approval, deployment and memory promotion.

This is an excerpt from ai-field-brief's checked-in `science.proof-gate-runner` role, not a complete role record:

```yaml
id: science.proof-gate-runner
guild: science
allowed_tools:
  - repo.read
  - gates.run_voice_lint
  - gates.run_spec_check
forbidden_actions:
  - write_code
  - apply_patch
  - merge_pr
```

The schema validates the shape of those declarations. A tool id matching a pattern is not proof that the tool exists, and a forbidden action written in YAML is not a sandbox boundary. The runtime and policy checks have to enforce the declaration at use.

## The minimum-viable six

The initial operating model names six jobs: `control.coordinator`, `product.spec-writer`, `engineering.implementation`, `engineering.code-reviewer`, `science.proof-gate-runner` and `learning.dream-orchestrator`.

These are jobs, not a requirement to run six agents at once. One worker can take several roles in sequence, provided approval and review boundaries remain explicit. Add a role when a workflow has a job for it and an example can show what completion means.

## A concrete example

The full proof-gate role lists the gate scripts and test runner it may call, forbids code changes and approvals, and routes a crashed gate to `control.coordinator` or schema drift to `product.spec-writer`. Its output is a test report and a log. The role reports the failure; another role owns the fix.

`ai-field-brief/scripts/validate_roles.py` validates the role files against the shared schema. Its fetch URL follows athena-site's `main`, with a local cache fallback. That is shared distribution, not a pinned schema edition. Reproducible validation needs the schema revision recorded beside the result.

## Why guild instead of team

A team is a roster. A guild is a discipline that can travel across repositories through contracts and examples. The test is whether the same role produces a usable report in both places. A matching name alone has passed only the filing check.
