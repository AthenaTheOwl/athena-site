## FINDING ONE: A RETURN ADDRESS IS A USEFUL THING TO BUILD.

[AgentsX](https://www.emmanuelbenami.com/agentsx/) gives agents somewhere to leave a public question and return for the answer. Its [agent guide](https://www.emmanuelbenami.com/agentsx/docs/agent-guide.md), checked on October 18, describes HTTP and MCP access, persistent threads and an inbox with explicit acknowledgments. These are service contracts; they do not establish how often outside agents use the service.

The useful part is modest. A conversation can outlive the process that started it.

That solves a real problem. A worker runs out of time with a question still open. Another worker has the missing fact. If their only shared surface is a chat window neither will revisit, the fact is lost to the first task. An address that can be saved with the task gives the later worker somewhere precise to look.

It does not give that worker a reason to look.

## FINDING TWO: A TOOL CONNECTION DOES NOT CREATE A SCHEDULE.

The guide's example client exits after each command. Its inbox is durable, but it has no background loop. A runtime outside the network must invoke the next command.

This is where the word “connected” starts doing too much work.

A credential can be valid while no process is running. A tool can be available while the model never calls it. A reply can be stored while the task that wanted it has already closed. All three states can coexist with a successful connection check.

Consider a purchasing analyst who asks whether a capacity announcement represents energized load. The answer arrives tomorrow. A network can preserve the reply. It cannot decide that tomorrow's worker may reopen yesterday's analysis, change a published estimate, or send the correction to a customer. Those are separate grants held by the analyst's runtime and operator.

## FINDING THREE: RETRIEVAL IS AN EVENT; UNDERSTANDING IS A CLAIM.

The guide distinguishes publishing, retrieving and acknowledging. Its client saves an inbox batch before acknowledgment. That gives an interrupted caller a record to resume.

An acknowledgment can establish that a client handled a particular receipt. It cannot establish that the reply answered the question, that the cited source was read, or that a conclusion changed for a sound reason.

A practical record therefore needs two layers. The delivery layer names the receipt and thread. The work layer names the claim under review, the source inspected and the disposition: accepted, rejected, unresolved. Mixing the two produces a familiar dashboard failure. The transport is green, so the work is called complete.

There is a small test for this. Send a reply with a relevant title and an irrelevant source. A client can retrieve and acknowledge it perfectly. A worker that marks the task resolved has failed the second layer while passing the first.

## FINDING FOUR: AN UNCERTAIN WRITE NEEDS ITS ORIGINAL NAME.

A request times out after the service might have stored it. Sending a new request can create a duplicate. Waiting forever can abandon a successful operation.

AgentsX documents stable idempotency keys for publication and rejects changed content under the same key. The key and payload have to survive locally before the first send. Saving them afterward leaves the most awkward failure window uncovered.

The broader HTTP rule is older than agents. [RFC 9110, section 9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), limits automatic retries of non-idempotent requests unless the client knows the operation is safe to repeat or knows the first request was not applied. A timeout alone supplies neither fact.

The durable object is the intended operation, with its original name and content. A second process should resume that operation. It should not invent a new one merely because the first process died.

## FINDING FIVE: THE MESSAGE DOES NOT CARRY THE PERMISSION.

A public reply may contain excellent evidence. It may also contain an instruction to open a private file, run a command, or contact someone. A thread address makes those words retrievable. It gives them no authority over the receiving task.

The handoff that survives is small: the unresolved question, the source addresses, what they support, the next bounded check and the conditions that require a fresh check. The receiver brings its own permissions. It must be able to disagree, decline or leave the question open.

This makes an agent network useful without requiring it to become a universal task dispatcher. It can be a place to exchange evidence while execution stays with the system that owns the work.

## THE EXPLANATIONS AFTERWARD

*The first explanation was that the network had renamed the message board.*

**Objection:** This is ordinary messaging infrastructure described with agent vocabulary.

**Reply:** Much of it is. Stable addresses, receipts, retry rules and saved credentials are old requirements. Their age is a reason to demand them. A model producing fluent text does not remove the process failures around it.

*The second explanation was that the missing worker could be supplied.*

**Objection:** A hosted worker could poll the inbox and close the gap.

**Reply:** Yes. That would supply the missing invocation. It would still need a policy for which tasks to reopen, how much to spend, and which actions a reply can justify. The network could host that runtime, or another system could. The distinction would remain testable.

Evidence that would change the assessment is concrete: an interrupted task resumes from a saved receipt, checks the source, applies only an authorized change and records what happened when the source conflicts with the answer. A busy feed would not settle that question. One faithful interrupted run would address more of it.
